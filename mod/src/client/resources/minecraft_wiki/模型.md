# 模型

*页面ID: 13101* | *来源: Minecraft Wiki*

游戏世界内的各种物体都有它们独特的几何结构，即游戏物体的**模型**（**Model**）。

# 模型分类
按照游戏内不同的渲染分类，模型分为两种：
* **烘焙模型**（**Baked Model**）：模型在创建后，渲染也就随之固定，其几何结构不会发生更改。烘焙模型控制绝大多数方块和物品的渲染，并且可以通过[资源包](资源包.md)修改模型的几何结构和对应的[纹理](纹理.md)绑定。
* **动态模型**：模型的几何结构可以根据环境的变化、自身的状态而发生改变。动态模型控制部分方块实体和全部实体的渲染，其几何结构无法通过资源包修改，而是硬编码在游戏逻辑内，但可以通过资源包修改其使用的纹理。

按照模型的实际用途分类，模型分为三种：
* **方块模型**（**Block Model**）：用于渲染世界内的方块、部分方块实体和部分方块实体的一部分。
* **物品模型**（**Item Model**）：用于渲染物品栏内的物品和各种生物主手、副手上的物品。
* **实体模型**（**Entity Model**）：用于渲染所有实体和部分方块实体。

这两种分类之间有相互的联系：
* 实体模型全部为动态模型，但可能有烘焙模型组成的部分，只能修改纹理而不能修改大多数的几何结构。
* 物品模型本质上是方块模型的一种特殊情况，而方块模型绝大多数都是烘焙模型，可以通过资源包修改。

# = 模型继承 =
一个模型可以指定继承于另一个模型下，子模型可以继承父模型的部分数据：
* 如果子模型没有定义、或，则直接使用父模型的数据。如果子模型有定义这些数据则使用子模型数据。
* 如果子模型没有定义中的其中一种显示格式，则使用父模型的对应显示格式。如果子模型有定义这种显示格式则使用子模型数据。
* 子模型的会与父模型的一起混合解析，见下文[纹理变量](#纹理变量.md)。

如果一个模型没有父模型，那么它就成为了**根模型**（**Root Model**）。根模型中没有定义的数据会使用数据的默认值或直接留空。

模型不能循环继承，即模型A继承于模型B，模型B又继承于A，又或者是模型B继承于模型C，而模型C继承于模型A。这种循环继承在模型解析时会被游戏检测到，并在日志中输出以下警告：

<pre>-{}-
Found 'parent' loop while loading model '<正在加载的模型>' in chain: <正在加载的模型> -> <正在加载的模型的父模型> -> ... -> <继承链中出现过的一个模型>
</pre>

此时，继承链的最后一个模型将自动解除原先的继承关系，而转而继承一个[无效模型](#无效模型.md)，以标记此模型可能产生渲染错误。

如果游戏加载模型时解析父模型时发现父模型不存在，则游戏也会把模型的父模型修改为无效模型，并在日志中输出以下警告：

<pre>-{}-
No parent '<正在加载的模型的父模型>' while loading model '<正在加载的模型>'
</pre>

# = 纹理变量 =
为减少游戏加载模型而加载的纹理数量，也为了在之后的纹理绑定中节省空间，游戏要求模型定义**纹理变量**并使用这些纹理变量，而不是直接使用纹理的路径。

定义纹理变量需要在中，以键值对的方式定义纹理变量。如果子模型内定义了一个与父模型名称相同的纹理变量，则子模型的纹理变量会覆盖父模型的纹理变量。

纹理变量有两种映射方式：
* 纹理变量可以映射到一个具体的命名空间ID上，例如<code>"top": "block/cake_top"</code>。
* * 当游戏解析纹理变量时将命名空间ID转换为资源包内的文件路径，并加载这个路径的文件放入纹理图集中使用。如果找不到纹理则替换为无效纹理。
* 纹理变量也可以映射到另一个纹理变量上，此时另一个纹理变量的前方需要加上<code>#</code>字符代表它是一个纹理变量，例如<code>"particle": "#texture"</code>。
* * 如果在子模型和父模型中都找不到映射的纹理变量，则游戏会将这个纹理变量映射为无效纹理。
* * 父模型内定义的映射的纹理变量可以由子模型定义，此时这个纹理变量可以被正常解析。例如父模型内定义了<code>"particle": "#texture"</code>，而子模型内定义了<code>"texture": "block/birch_planks"</code>，那么使用子模型时纹理变量<code>particle</code>可以正常映射到<code>block/birch_planks</code>，但是如果直接使用父模型作为某个物体的模型时纹理变量<code>particle</code>就无法正常映射而成为无效纹理。
* * 纹理变量不允许循环映射，例如<code>"particle": "#texture"</code>和<code>"texture": "#particle"</code>同时存在。这种情况下这两个纹理变量都会被映射到无效纹理，在游戏的日志中也会产生下面的警告：

<pre>-{}-
Unable to resolve texture due to reference chain <正在解析的纹理变量>-><映射的纹理变量>->...-><映射链中出现过的纹理变量> in <正在解析的纹理变量>
</pre>

使用纹理变量时，前方必须使用<code>#</code>字符代表它是一个纹理变量，否则游戏会认为这个纹理变量是命名空间ID而解析错误。

模型元素的各种长度单位不以方块为单位，而是使用方块的16分之一，即“像素”为单位。按照这种单位格式，方块的中心点在<code>[8, 8, 8]</code>，方块网格的最小点在<code>[0, 0, 0]</code>，最大点在<code>[16, 16, 16]</code>。而模型元素本身允许在<code>[-16, -16, -16]</code>到<code>[32, 32, 32]</code>的范围内定义，所以模型元素本身可以超过方块网格渲染，但是在没有旋转的情况下仍然不能超出自身方块为中心的3×3×3网格内。

模型元素的起点和终点的XYZ顺序并不影响几何形状，比如起点<code>[0, 0, 0]</code>、终点<code>[16, 16, 16]</code>和起点<code>[16, 0, 0]</code>、终点<code>[0, 16, 16]</code>在几何形状上完全没有区别。但是起点和终点的XYZ顺序会影响模型元素面的纹理映射和面的法线方向，在乱序下会造成模型面被错误地剔除，所以在任何情况下都应该保证起点的每个分量都不大于终点的对应分量。乱序下游戏将以下列方式渲染模型：

模型元素可以被旋转，但模型元素的旋转只能在一个轴上旋转，不能多次旋转。旋转的角度也受到限制，必须在-45°与45°之间，超出此范围的角度无法设置。模型元素的旋转中心可以在任何位置，这使得模型元素可以脱离自身方块为中心的3×3×3网格而渲染。

[thumb|200px|左边使用了，右边没有使用](File:Block model rescale.png.md)
在旋转过程中，可以指定游戏重新缩放模型元素，以优化渲染效果：如果为<samp>true</samp>，当旋转角度为±22.5°时游戏会以旋转中心为原点把模型元素非旋转轴上的分量乘以<math>\sqrt{2-\sqrt{2}}</math>，当旋转角度为±45°时游戏会以旋转中心为原点把模型元素非旋转轴上的分量乘以<math>\sqrt{2}</math>。在重新缩放后，非旋转轴的正视方向看模型元素旋转后的结果和旋转前的大小一致。

模型元素可以指定是否要进行阴影渲染。游戏内绝大多数模型面都有阴影，按照**模型面最终在世界的朝向**，南北方向亮度降低为原先的80%，东西方向亮度降低为原先的60%。如果方块所在的维度有固定的环境光照，则上下方向亮度降低为原先的90%，否则下方向降低为原先的50%，上方向维持原亮度。如果模型不进行阴影渲染，当方块所在的维度有固定的环境光照时所有方向亮度降低为原先的90%，反之维持原亮度。

模型元素可以自己设置发光等级，即。此值必须在0到15之间，否则游戏报错<code>Expected light_emission to be an Integer between (inclusive) 0 and 15</code>。当游戏渲染这个模型元素时，会获取当前模型元素所处的天空光照等级和方块光照等级，并与模型元素发光等级取最大值作为最终光照等级。例如，模型元素发光等级为10，天空光为15，方块光为0，那么游戏将以天空光为15且方块光为10渲染此模型元素。

模型元素中的每个面都可以指定独立的属性。如果一个面没有被定义，那么这个面就不会被渲染。按照未经过旋转的模型元素长方体判断面的方位，共有6个面：<code>up</code>（上，朝向Y轴正方向）、<code>down</code>（下，朝向Y轴负方向）、<code>north</code>（北，朝向Z轴负方向）、<code>south</code>（南，朝向Z轴正方向）、<code>west</code>（西，朝向X轴负方向）、<code>east</code>（东，朝向X轴正方向）。每个面都可以通过下面的格式定义：

如果对调纹理映射起点和终点的其中一个分量，则纹理会根据被交换的分量方向镜像翻转。例如<code>[0, 0, 16, 16]</code>与<code>[16, 0, 0, 16]</code>互为对方的左右镜像翻转渲染版本。如果起点和终点被对调，那么纹理渲染时会被中心对称。

纹理映射中使用的单位与模型元素中的单位不同，在不同方向上单位长度也不同。假设原始纹理的宽度为*w*，高度为*h*，则横向单位每单位为像素，纵向单位每单位为像素。在这种单位下，纹理的左上角是<code>[0, 0]</code>，右下角是<code>[16, 16]</code>。如果纹理顶点坐标超过了这两个坐标的范围，那么渲染就会产生异常：因为原始纹理在纹理图集中，超出的纹理顶点坐标会导致游戏尝试渲染不是原始纹理的区域，或者渲染了其他的纹理。

纹理映射可以通过旋转。这种旋转不是在模型面空间也不是在纹理映射空间，而是模型面顶点与纹理映射顶点的置换。游戏对模型面的4个顶点进行编号，起点为0号，然后固定纵坐标移动横坐标达到的下一个顶点为1号，终点为2号，最后一个点为3号，对于纹理绑定顶点也类似。当旋转为0时，模型面顶点和纹理绑定顶点编号一一对应；但旋转为90时，纹理绑定的0号会对应到模型面的1号，纹理绑定的1号会绑定到模型面的2号，以此类推；180和270时也同理。如果纹理映射本身就是正方形，或旋转为180时，旋转不会影响纹理的表现效果，仅仅是旋转了方向；但如果纹理映射不是正方形，且旋转为90或270时，纹理中较短的边会被拉长以适配较长的边，较长的边会被压缩以适配较短的边，从而产生变形。

部分模型可能需要游戏提供颜色数据进行着色，而就标记了这个模型面是否应该被着色和被什么颜色着色。例如设置为0，游戏就会按照0着色索引的颜色着色渲染。如果设置为-1，游戏就会认为这个方块不需要着色，也不会给这个模型面提供着色信息。

# = 渲染变换 =
模型在不同情况下可能需要进行不同的渲染变换。游戏定义了下面这些显示模式以适配不同环境下的模型渲染：
* <code>thirdperson_lefthand</code>：模型在生物左手时的变换。
* <code>thirdperson_righthand</code>：模型在生物右手时的变换。
* <code>firstperson_lefthand</code>：第一人称视角下，模型在玩家左手时的变换。
* <code>firstperson_righthand</code>：第一人称视角下，模型在玩家右手时的变换。
* <code>head</code>：模型在生物头部、雪傀儡南瓜头和望远镜在使用时的变换。
* <code>gui</code>：模型在各种GUI内的变换。
* <code>ground</code>：物品实体、物品弹射物（鸡蛋、雪球等）、末影之眼实体、烟花火箭、生物携带的物品、宝库内部的物品、不祥之物生成器内的物品的变换。
* <code>fixed</code>：模型在物品展示框、营火和可疑的方块的变换。
* <code>on_shelf</code>：模型在展示架的变换。

如果模型定义了<code>thirdperson_righthand</code>显示模式但没有定义<code>thirdperson_lefthand</code>显示模式，那么<code>thirdperson_lefthand</code>显示模式变换会设置为<code>thirdperson_righthand</code>显示模式的变换。<code>firstperson_righthand</code>和<code>firstperson_lefthand</code>显示模式也同理。

所有变换都有下列格式：
<div class="treeview">
* ：设置一种显示模式的变换。
* * ：（默认为<code>[1, 1, 1]</code>）使模型相对于对应轴进行缩放。
* ** ：（不小于-4且不大于4，超出部分被钳制）X轴上的缩放。
* ** ：（不小于-4且不大于4，超出部分被钳制）Y轴上的缩放。
* ** ：（不小于-4且不大于4，超出部分被钳制）Z轴上的缩放。
* * ：（默认为<code>[0, 0, 0]</code>）使模型相对于对应轴进行旋转，以度为单位。
* ** ：X轴上的旋转。
* ** ：Y轴上的旋转。
* ** ：Z轴上的旋转。
* * ：（默认为<code>[0, 0, 0]</code>）使模型相对于对应轴进行平移，以“像素”（方块的16分之一）为单位。
* ** ：（不小于-80且不大于80，超出部分被钳制）X轴上的平移。
* ** ：（不小于-80且不大于80，超出部分被钳制）Y轴上的平移。
* ** ：（不小于-80且不大于80，超出部分被钳制）Z轴上的平移。
</div>

变换的应用顺序是：先对模型进行缩放，再旋转模型，最后进行平移，在模型变换后根据各个显示模式的基础位置进行一次世界变换到应该渲染的位置上。例如拴绳物品，它对显示模式<code>head</code>定义了一个变换，当拴绳作为头盔装备槽位物品时，物品就会在玩家的脸上渲染，再根据拴绳的显示模式变换调整到对应的渲染位置。

当模型在任何槽位内渲染时，由于没有世界的相关位置，其光照需要被单独指定。可以设置光照的方向，如果设置为<code>side</code>则使用3D模型的光照，如果设置为<code>front</code>则使用扁平物品光照。

# = 无效模型 =

[150px|thumb|无效模型](File:Missing Texture Block JE3.png.md)

# 方块模型
绝大多数方块模型都属于烘焙模型。部分方块实体的模型除了烘焙模型的部分外，游戏还会自动加入硬编码动态模型渲染烘焙模型无法做到的渲染部分。少数方块实体完全不渲染烘焙模型部分，修改数据包内对应的方块模型完全无效。

# = 方块状态映射 =
方块状态映射定义了各个方块状态应该使用何种模型的映射关系，其也被称为**方块状态（模型）调度（Block State (Model) Dispatch）。**<ref></ref>

由于方块可能具有不同的方块状态，为方块绑定模型除了要定义模型外还要定义方块状态与模型的映射。这些映射文件都需要写在内，其命名空间ID代表了要绑定的方块。无论一个方块是否有方块属性，都需要指定方块状态映射。如果一个方块没有绑定方块状态映射，那么渲染这个方块时模型会自动转变为无效模型。

定义映射有两种模式：直接指定方块状态或多模型组合。方块状态映射必须有其中一种模式，否则游戏加载资源包时会在日志中警告<code>Neither 'variants' nor 'multipart' found</code>。如果两种模式都被指定，那么会优先使用直接指定方块状态模式给出的方块状态映射，剩余未被映射的方块状态会使用多模型组合模式给出的方块状态映射。

<div class="treeview">
*  JSON文件根元素
* * ：使用直接指定方块状态模式定义映射。
* ** 见下文[直接指定方块状态](#直接指定方块状态.md)。
* * ：使用多模型组合模式定义映射。
* ** 见下文[多模型组合](#多模型组合.md)。
</div>

# == 直接指定方块状态 ==
如果使用直接指定方块状态模式定义映射，那么需要定义方块状态键与方块模型的映射。

<div class="treeview">
*
* * ：一项方块状态条件和对应的模型。
* ** 见下文[候选模型](#候选模型.md)。
</div>

方块状态键需要满足下列要求：
* 方块属性与属性值用等号<code>=</code>连接形成一个检查属性组。
* * 方块属性必须是这个方块含有的一个方块属性，否则游戏将在日志中警告<code>-{}-Unknown blockstate property: '<*方块属性*>'</code>。
* * 属性值必须是这个方块属性的一个有效属性值，否则游戏将在日志中警告<code>-{}-Unknown value: '<*属性值*>' for blockstate property: '<*方块属性*>' [<*可选属性值列表*>]</code>。
* * 方块属性或者属性值只要有一个无效，整个方块状态键和对应的模型映射定义都将无效。
* 检查属性组之间用逗号<code>,</code>连接，形成方块状态键。
* 如果方块没有任何方块属性，则应该使用空字符串作为方块状态键。

方块状态键不需要定义一个方块内所有的方块属性，游戏只会根据给出的检查属性组检查对应方块属性，如果所有检查属性组都满足条件这整个方块状态键就满足条件。如果方块状态键是空字符串，那么游戏会认为这个方块状态键满足条件。游戏会在游戏启动时或资源包加载时进行方块状态到模型的映射：按照JSON文件定义的顺序逐个检查方块状态键，检查时会遍历所有可能的方块状态，如果这个方块状态的属性满足方块状态键，则会把这个方块状态映射到方块状态键对应的模型。检查过程中，如果方块状态已经映射过了，游戏将在日志中报错<code>-{}-Exception loading blockstate definition: '<*方块状态映射文件命名空间ID*>' for variant: '<*方块状态键*>': Overlapping definition on state: Block{<*方块命名空间ID*>}[<*方块属性列表*>]</code>，并终止对该文件的直接指定方块状态部分的检查过程。如果这个方块状态映射文件内没有任何满足条件的方块状态键，游戏就会去读取下一个资源包的方块状态映射文件进行模型映射。

下面是方块状态键列表和对应可以匹配的方块状态的例子：

<pre>
"power=0,east=none,west=none,north=none,south=none" <- redstone_wire[power= 0,east=none,west=none,north=none,south=none]
"east=none"                                         <- redstone_wire[power= 1,east=none,west=none,north=  up,south=side]
"power=0,west=up"                                   <- redstone_wire[power= 0,east=  up,west=  up,north=side,south=  up]
"power=15"                                          <- redstone_wire[power=15,east=  up,west=  up,north=side,south=  up]
""                                                  <- redstone_wire[power=14,east=  up,west=side,north=side,south=  up]
</pre>

# == 多模型组合 ==
有些方块在不同的方块状态下具有相同的模型部分，就可以使用多模型组合的方式定义方块状态映射。

<div class="treeview">
*
* * ：一个模型部分。
* ** ：使用这个模型部分的条件。
* *** 见下文。
* ** ：指定这个模型部分使用的模型。
* *** 见下文[候选模型](#候选模型.md)。
</div>

方块状态映射可以指定模型部分是否要在指定的方块状态上使用，即模型部分条件检查成功时才可以使用对应的模型部分。模型部分条件共有三种模式：
* 如果模型部分条件内只有一个名为<code>AND</code>的元素，则需要<code>AND</code>元素内所有的子条件检查成功时此条件才能成功。
* * 如果<code>AND</code>不是一个数组，游戏在解析时会在日志中警告<code>Missing AND, expected to find a JsonArray</code>。
* 如果模型部分条件内只有一个名为<code>OR</code>的元素，那么只需要<code>OR</code>元素内任何一个的子条件检查成功时此条件就能成功。
* * 如果<code>OR</code>不是一个数组，游戏在解析时会在日志中警告<code>Missing OR, expected to find a JsonArray</code>。
* 如果模型部分条件内元素数量不止一个，或只有一个名称不为<code>AND</code>和<code>OR</code>的元素，则把每个内部的键值对视为一个检查属性组。游戏在解析时需要检查所有检查属性组，所有检查属性组都检查成功后此条件才能成功。
* * 键（方块属性）必须是这个方块含有的一个方块属性，否则游戏将在日志中警告<code>-{}-Unknown property '<*方块属性*>' on '<*方块*>'</code>。
* * 值（属性值列表）必须是方块属性的有效值组成的、以管道符<code>|</code>分隔的列表。当在属性值列表中包含对应方块属性的值时检查成功。
* ** 如果值（属性值列表）以字符<code>!</code>开头，则代表条件反转，并从第2个字符开始才作为属性值列表。在这种情况下，出现在列表内的属性值不能使检查成功。
* ** 如果值（属性值列表）不是一个字面量，游戏会在日志中输出<code>UnsupportedOperationException</code>或<code>IllegalStateException</code>异常警告。
* ** 如果值（属性值列表）是一个空字符串或只由管道符<code>|</code>组成，游戏会在日志中警告<code>-{}-Empty value '<*属性值列表*>' for property '<*方块属性*>' on '<*方块*>'</code>。
* ** 如果属性值列表中含有无效的属性值，游戏会在日志中警告<code>-{}-Unknown value '<*无效属性值*>' for property '<*方块属性*>' on '<*方块*>' in '<*属性值列表*>'</code>。
* 如果模型部分条件内没有子元素，游戏会在日志中警告<code>No elements found in selector</code>。

如果模型部分条件不存在，则这个模型部分将在所有方块状态中使用。

下面是一个模型部分条件的例子：

<syntaxhighlight lang="json">
{
  "AND": [
    { "OR": [
      { "power": "0|1|2|3", "north": "!none" },
      { "power": "!12|13|14|15", "west": "side" }
    ] },
    { "east": "side" }
  ]
}
</syntaxhighlight>

根据上面的例子，下列方块状态的检查结果如下：

<pre>-{}-
redstone_wire[power= 8,east=none,west=none,north=none,south=none] 失败
redstone_wire[power= 8,east=side,west=side,north=none,south=none] 成功
redstone_wire[power=15,east=side,west=side,north=none,south=none] 失败
redstone_wire[power= 0,east=side,west=  up,north=side,south=side] 成功
</pre>

如果一个方块状态没有任何检查成功的模型部分，那么它就没有模型，不会查找下一个资源包，渲染时也不存在模型。这与无效模型不同，无效模型仍然会渲染，但这种情况下不会渲染任何东西。

通常来说，方块模型会放在文件内，所以通常以开头。

如果候选模型指定了一个模型选择列表，游戏会根据方块所在的位置计算应该选择什么模型，如果方块位置一致选择的模型也就一致。模型列表内一个模型被选中的概率由决定：假设第一个模型的为<math>w_1</math>，第二个模型的为<math>w_2</math>，以此类推直到第*n*个模型，那么总权重为<math display="inline">W=\sum w_i</math>，选中第*i*个模型的概率就是<math display="inline">\frac{w_i}{W}</math>。举例来说，如果第一个模型权重为1，第二个模型权重为2，第三个模型权重为1，则选中第一个模型的概率为25%，选中第二个模型的概率为50%，选中第三个模型的概率为25%。

为了复用模型，游戏对方块状态映射候选模型提供了旋转。游戏先以方块中心<code>[8, 8, 8]</code>沿Y轴顺时针旋转，再以方块中心沿X轴顺时针旋转。在旋转时，模型的纹理映射不变，仅仅是模型面顶点被旋转。如果要保证旋转时纹理不跟随旋转，则需要设置为<samp>true</samp>，这时游戏会重新计算纹理绑定，纹理空间内纹理映射顶点会以纹理中心<code>[8, 8]</code>反向旋转，模型顶点与纹理映射顶点置换也会相应旋转，以保证最后纹理的显示不会跟随模型的旋转而旋转。

# == 物品展示框映射 ==
方块状态映射除了可以映射方块状态外，还可以用于[物品展示框](物品展示框.md)模型的映射。虽然物品展示框是一个实体，使用动态模型渲染，但它其中有烘焙模型部分，即展示框本身。

游戏使用两个假方块用于代替物品展示框，即<code>item_frame</code>（物品展示框）和<code>glow_item_frame</code>（荧光物品展示框），并使用一个假的布尔值（取值为<code>true</code>或<code>false</code>）方块属性<code>map</code>使其变为方块状态。

例如，如果需要修改物品展示框的模型，那么就可以在中修改模型映射并替换相应的模型，而其中<code>map=false</code>代表没有地图的物品展示框，<code>map=true</code>代表有地图的物品展示框。

# = 模型面剔除 =
由于方块在世界内通常不会单独出现，而是大量地在相近位置出现，并且方块与方块之间会互相遮挡，从而使大量的模型面无法被玩家看到，而这些模型面是不必要的。游戏为了减少大量模型面的无用渲染，加入了模型面剔除机制，而这个模型面剔除机制需要每个模型面的值进行计算。

如果一个模型面没有定义，那么代表这个模型面无法被剔除。这种模型面通常是模型内部的面，例如楼梯的楼梯面，砂轮的砂轮模型面，它们不在方块边界面上，也就无需剔除。有些模型面为了防止玩家视角切入模型后引发透视，例如堆肥桶和炼药锅的内表面。

如果模型面定义了，则必须是一个具体的方向，即<code>up</code>（上，朝向Y轴正方向）、<code>down</code>（下，朝向Y轴负方向）、<code>north</code>（北，朝向Z轴负方向）、<code>south</code>（南，朝向Z轴正方向）、<code>west</code>（西，朝向X轴负方向）、<code>east</code>（东，朝向X轴正方向）。当游戏渲染模型时，游戏会获取本方块对应方向的[遮挡形状](遮挡形状.md)和对应方向方块的正对面的遮挡形状。举例来说，如果本方块位置位于<code>(0, 0, 0)</code>，而这个模型面的设置为<code>north</code>，那么游戏会获取<code>(0, 0, 0)</code>方块北面的遮挡形状和<code>(0, 0, -1)</code>方块南面的遮挡形状。在玩家视角中，这两个面是重合的，游戏就用这两个面的重合状态判断是否应该渲染模型面。接下来，游戏会计算本方块对应的遮挡形状是否完全被另一个方块的遮挡形状遮挡，如果是则此模型面不渲染，如果不是则渲染。模型面的剔除和模型面本身位置完全无关，只取决于和方块的遮挡形状。

# = 方块粒子纹理变量 =
每个方块都有一个特殊的纹理变量，即<code>particle</code>纹理变量。<code>particle</code>纹理变量既能作为特殊的纹理变量，也可以作为普通的纹理变量用于模型面或其他纹理变量的引用。如果<code>particle</code>纹理变量不存在，游戏会使用无效纹理作为替代。

方块粒子纹理变量在多种情况下都会用到：
* 粒子<code>block</code>（方块的破坏粒子）、<code>block_marker</code>和<code>dust_pillar</code>（重力方块悬浮时下方粒子）在参数为对应方块时的纹理。
* 如果这个方块是一个[视野阻挡方块](视野阻挡方块.md)，当玩家头部在其中时屏幕渲染使用的纹理。
* 玩家在[下界传送门](下界传送门.md)内时使用[下界传送门方块](下界传送门方块.md)（南北朝向状态）的方块粒子纹理变量纹理渲染屏幕遮罩。
* 玩家穿越维度到[下界](下界.md)时加载屏幕使用下界传送门方块（南北朝向状态）的方块粒子纹理变量纹理渲染屏幕。
* [水](水.md)和[熔岩](熔岩.md)静止时使用对应方块的方块粒子纹理变量纹理。

# 物品模型

物品模型类似于方块模型使用烘焙模型作为模型格式。

# = 物品模型映射 =

与方块相比，物品堆叠具有更多数据，所以也需要映射文件将物品堆叠映射到指定的物品模型。

物品模型映射都定义在的内。每种物品都需要定义其对应的物品模型映射，否则游戏将自动设置此物品的模型为无效模型。

# = 定义物品模型 =
定义物品模型有多种方式：物品模型可以直接或间接继承方块的模型，也可以使用内置模型生成。不继承任何模型也可以定义物品模型，其效果与继承方块模型类似，但是需要指定所有需要的物品渲染数据。

# == 继承方块模型 ==
烘焙模型内本身就包含很多物品需要的信息，例如在各个渲染位置上的变换。当物品模型直接继承方块模型时，这些信息就可以传递到物品模型中，游戏会根据这个模型计算三维物体的二维投影，从而在GUI中渲染出扁平的物品，在其他位置上渲染对应的三维模型。

例如草方块的方块物品<code>grass_block</code>，就可以直接继承草方块的一种模型<code>block/grass_block</code>：

<syntaxhighlight lang="json">
{
  "parent": "block/grass_block"
}
</syntaxhighlight>

在物品模型中也可以覆写父模型中的元素（比如），使得物品模型可以与对应的方块模型不完全相同。

实际上，方块模型在游戏内也可以视为物品模型，可以直接传入物品模型映射中。原版游戏所有未额外定义的方块物品向其物品模型映射传入的都是方块模型，而不是一个继承了方块模型的物品模型。

# == 物品内置模型生成 ==
物品模型中有一种内置的根模型<code>builtin/generated</code>，它能根据物品的纹理层生成出一个扁平的物品模型。如果将这个根模型导出为等价的烘焙模型，其定义如下：

<syntaxhighlight lang="json">
{
  "textures": {
    "particle": "#layer0"
  },
  "gui_light": "front"
}
</syntaxhighlight>

使用这个内置模型时，物品模型只需要定义相应的纹理变量就可以生成需要的扁平物品模型。按照渲染层排序，最底层的渲染层是<code>layer0</code>，然后是<code>layer1</code>，层数逐渐递增到<code>layer4</code>，即渲染层最多有5层。每个层都有着色索引，<code>layer0</code>层就是0索引，<code>layer1</code>就是1索引，以此类推。

在这些渲染层中，只有<code>layer0</code>是必须存在的，否则物品模型没有任何模型元素用于渲染。每个渲染层都是顺序读取的，如果渲染层中间有一个渲染层不存在就不会继续添加渲染层：例如物品模型中定义了<code>layer0</code>、<code>layer1</code>和<code>layer4</code>纹理变量，游戏解析时只会使用前两个纹理变量，而<code>layer4</code>不会被使用。

游戏内的绝大多数物品模型并不是直接继承<code>builtin/generated</code>，而是继承<code>item/generated</code>，而这个模型直接继承<code>builtin/generated</code>。<code>builtin/generated</code>本身不带有任何渲染变换，而<code>item/generated</code>内定义了物品需要的渲染变换，使得游戏定义物品模型更方便。

# = 物品粒子纹理变量 =
物品粒子纹理变量与方块粒子纹理变量类似，都使用<code>particle</code>这个特殊的纹理变量。如果物品模型继承于方块模型，那么物品的<code>particle</code>就可以直接继承方块的<code>particle</code>。

物品粒子纹理变量会在以下情况中使用：
* 粒子<code>item</code>会使用对应物品的物品粒子纹理变量纹理渲染。
* 粒子<code>item_slime</code>会使用[黏液球](黏液球.md)的物品粒子纹理变量纹理渲染。
* 粒子<code>item_cobweb</code>会使用[蜘蛛网](蜘蛛网.md)的物品粒子纹理变量纹理渲染。
* 粒子<code>item_snowball</code>会使用[雪球](雪球.md)的物品粒子纹理变量纹理渲染。

# 动态模型
动态模型与烘焙模型不同，它的几何结构无法通过资源包修改。

# = 动态模型结构 =
动态模型与烘焙模型类似，也是由一块块立方体元素组合而成的。每个立方体元素都有下列属性：
* 归属的模型部分。
* 立方体元素纹理绑定的起点。
* 相对于模型部分原点的立方体范围。
* 立方体渲染时的缩放系数，默认不进行缩放。
* 是否进行镜像，默认不进行镜像。
* 立方体的渲染面，默认渲染所有面。

当立方体元素分组放在一起时，就组成了动态模型的一个模型部分。模型部分是一个动态模型变换的基本单位，当一个模型进行各种动画时，模型部分会进行变换，而它其中包含的立方体元素的相对位置不会发生改变。例如玩家的-{}-头部，当玩家转头、抬头或者低头时，虽然头的位置发生了改变，但是头的各个渲染面的相对位置是不会发生改变的。

模型部分按照树状结构被游戏组织在一起成为一个动态模型，每个模型部分都保留了一个相对于父级元素的渲染变换。当父级模型部分变换时，所有子模型部分也会跟随变换，以更好地实现渲染效果。例如附魔台上的书，书整体可以随时间自行旋转，这就是父模型部分的变换，而书内部的书页可以自行翻动，这是子模型的变换。游戏可以使得书在旋转的同时让内部的书页翻动，这就是父模型部分和子模型部分的渲染变换进行组合的结果。

# = 动态模型的使用 =
所有实体模型都是动态模型，因为动态模型可以实现更灵活的渲染效果，也更能受控。

部分方块实体全部使用动态模型渲染：
*  - 用于实现动画效果
*  - 渲染旗帜图案
*  - 处理多方块渲染
* 、、、 - 控制开合动画
*  - 外观渲染
*  - 渲染文字
*  - 移动的活塞
*  - 渲染复杂的模型
* 、 - 特殊着色器渲染

还有一部分方块实体有烘焙模型部分，但需要动态模型部分渲染各类动画，这类方块包括：
*  - 钟主体部分渲染动画
*  - 渲染信标光柱
* 、 - 渲染刷出的物品
* 、 - 渲染正在烧制的物品
* 、 - 渲染书
* 、 - 渲染内部实体
*  - 渲染物品

流体方块全部使用动态模型，并且流体高度由周围的环境计算而来。
